# 마비노기 모바일 계산기

## 1. 프로젝트 개요

이 프로젝트의 목표는 **마비노기 모바일 계산기** 웹사이트를 만드는 것이다.

사용자가 게임에서 확인한 데이터를 웹페이지에 입력하면 JavaScript가 해당 데이터를 바탕으로 필요한 계산을 수행하고 결과를 화면에 표시한다.

프로젝트의 요구사항은 이 README.md와 각 파일에 대응하는 `README_[file_name]` 문서를 기준으로 관리한다.

## 2. 운영 환경

- GitHub Repository에서 모든 소스코드를 관리한다.
- GitHub Pages를 이용하여 웹사이트를 외부에 공개하는 것을 기본으로 한다.
- 정적 웹사이트를 기본 구조로 한다.
- HTML, CSS, JavaScript를 사용한다.
- PHP는 사용하지 않는다.
- 별도의 웹 애플리케이션 서버를 운영하지 않는다.
- 별도의 데이터베이스 서버를 사용하지 않는다.
- 별도의 유료 서비스 사용 없이 운영하는 것을 목표로 한다.

## 3. 사용자 데이터 처리

사이트는 사용자 계정을 관리하지 않는다.

다음 기능은 기본적으로 사용하지 않는다.

- 회원가입
- 로그인
- ID / Password
- 관리자 계정
- 사용자별 서버 데이터 저장
- 개인정보 수집

사용자가 입력한 게임 데이터는 서버 또는 데이터베이스에 저장하지 않는다.

## 4. JSON 데이터 파일

사용자가 입력한 게임 데이터를 JSON 파일로 저장하고 다시 불러올 수 있어야 한다.

### 저장

사용자가 입력한 데이터를 JavaScript로 JSON 형식으로 변환하여 사용자의 PC에 파일로 다운로드할 수 있도록 한다.

### 불러오기

사용자가 저장해 둔 JSON 파일을 웹페이지에서 선택하면 JavaScript가 파일을 읽고 기존 입력 데이터를 복원할 수 있도록 한다.

기본적인 데이터 흐름은 다음과 같다.

사용자 입력
→ JavaScript
→ JSON 생성
→ 사용자 PC에 다운로드

JSON 파일
→ 웹페이지에서 불러오기
→ JavaScript로 읽기
→ 입력값 복원
→ 계산 수행

## 5. 계산 기능

웹페이지에서 사용자가 입력한 마비노기 모바일 게임 데이터를 이용하여 계산을 수행한다.

계산은 기본적으로 사용자의 브라우저에서 JavaScript로 처리한다.

계산 결과는 웹페이지에 표시한다.

구체적인 계산 대상과 공식은 해당 기능에 대응하는 `README_[file_name]` 문서에 정의한다.

## 6. 사용자 환경 및 UI

웹사이트는 모바일 환경과 PC 환경을 모두 지원한다.

사용자의 환경에 따라 단순히 화면 비율만 변경하는 것이 아니라, 화면 크기와 기기 환경 등을 고려하여 적절한 UI를 제공한다.

### PC 환경

이상적인 PC 화면은 표준 화면비인 **가로:세로 = 16:9**를 기준으로 한다.

기본적으로 **1280x720 ~ 1920x1080** 범위의 화면 환경을 이상적인 PC 환경으로 고려한다.

페이지의 최소 크기는 **700x700**으로 한다.

PC 환경에서는 다음 사항이 발생하지 않도록 구성한다.

- 의도하지 않은 줄넘김
- UI 요소 또는 박스가 화면 밖으로 벗어나는 현상
- 콘텐츠가 서로 겹치는 현상
- 화면 크기에 따라 기능을 사용할 수 없게 되는 현상

### 모바일 환경

모바일 화면은 **가로:세로 = 9:19.5** 비율을 기본적인 모바일 화면비로 고려한다.

동시에 스마트폰뿐만 아니라 패드 및 플렉서블 기기의 다양한 화면비를 고려하여 **4:3 비율까지 폭넓게 호환**할 수 있도록 구성한다.

예시 환경:

- 1080x2340
- 1440x1080

모바일 환경에서도 화면비나 크기의 차이로 인해 의도하지 않은 줄넘김, UI 요소 또는 박스의 화면 이탈, 콘텐츠 겹침 등의 문제가 발생하지 않아야 한다.

### 공통 UI 원칙

- 모바일 환경에서는 모바일 화면에 적합한 UI를 제공한다.
- PC 환경에서는 넓은 화면에 적합한 UI를 제공한다.
- 모바일과 PC 환경의 특성에 따라 글자 크기, 입력 요소, 버튼, 여백, 배치 등 UI 크기와 표시 방식을 적절하게 조정한다.
- 화면 크기에 따른 반응형 UI를 적용한다.
- 필요한 경우 모바일 환경과 PC 환경을 구분하여 서로 다른 UI 구성을 적용할 수 있다.
- 환경 구분과 반응형 UI를 함께 사용하여 각 환경에서 사용하기 적합한 화면을 제공한다.
- 화면 크기와 화면비가 기준 환경과 달라지더라도 페이지의 주요 기능과 UI가 정상적으로 사용 가능해야 한다.
- 구체적인 UI 구성과 환경별 차이는 해당 기능 및 UI 파일에 대응하는 `README_[file_name]` 문서에 정의한다.

## 8. 프로젝트 파일 구조 및 위치

프로젝트의 실제 웹페이지 구성 파일은 역할에 따라 다음 위치에 분리하여 관리한다.

```
Mobi Calculator/
├── README.md
├── *.html
├── readme_files/
│   └── README_[file_name]
├── pages_css/
│   └── *.css
└── pages_js/
    └── *.js
```

### 파일 위치 규칙

- HTML 페이지 파일은 `Mobi Calculator/` 바로 아래에 둔다.
- HTML 파일에 대응하는 요구사항 문서는 `Mobi Calculator/readme_files/`에 둔다.
- CSS 파일은 `Mobi Calculator/pages_css/`에 둔다.
- JavaScript 파일은 `Mobi Calculator/pages_js/`에 둔다.
- 프로젝트 전체 요구사항을 관리하는 메인 `README.md`는 HTML 파일과 같은 `Mobi Calculator/` 바로 아래에 유지한다.
- 파일을 생성할 때는 파일 종류에 따라 위의 위치 규칙을 따른다.
- 파일을 참조할 때는 실제 저장 위치를 기준으로 경로를 작성한다. 예를 들어 HTML에서 CSS와 JavaScript를 참조할 경우 각각 `pages_css/파일명.css`, `pages_js/파일명.js`를 사용한다.
- 파일별 요구사항 문서를 확인할 때는 `readme_files/README_[file_name]` 경로를 사용한다.
- 기존 파일을 이동하거나 위치를 변경하는 경우 HTML의 상대 경로와 관련 요구사항 문서의 파일 경로 설명도 함께 확인한다.

### 현재 파일 구조 예시

| 종류 | 위치 | 예시 |
|---|---|---|
| 메인 요구사항 문서 | `Mobi Calculator/` | `README.md` |
| HTML 페이지 | `Mobi Calculator/` | `table.html`, `test.html` |
| 파일별 요구사항 문서 | `Mobi Calculator/readme_files/` | `README_table.html` |
| CSS | `Mobi Calculator/pages_css/` | `table.css` |
| JavaScript | `Mobi Calculator/pages_js/` | `table.js`, `test-data.js` |

## 9. 파일별 요구사항 문서

웹페이지를 구성하는 각 파일은 해당 파일과 1:1로 대응하는 `README_[file_name]` 문서를 생성하여 관리한다.

예를 들어:

```
index.html
README_index.html

style.css
README_style.css

script.js
README_script.js
```

각 `README_[file_name]` 문서에는 해당 파일의 역할, 구현 요구사항, 관련 동작 및 해당 파일을 수정할 때 확인해야 하는 조건을 기록한다.

파일을 생성하거나 수정할 때는 해당 파일의 `README_[file_name]` 문서를 함께 참조한다.

새로운 웹페이지 구성 파일이 추가되면 반드시 해당 파일에 대응하는 `README_[file_name]` 문서도 함께 생성한다.

웹페이지 구성 파일을 삭제하거나 역할이 변경되는 경우에는 대응하는 `README_[file_name]` 문서의 상태도 함께 확인하고 갱신한다.

파일별 세부 요구사항과 구현 기준은 해당 파일의 `README_[file_name]` 문서를 우선적으로 참조한다. 여러 파일에 영향을 미치는 공통 요구사항은 README.md와 각 관련 파일의 요구사항 문서를 함께 확인한다.

## 9. 프로젝트 개발 원칙

- 명시하지 않은 것은 임의로 해석 또는 결정해서 수정하지 않는다.
- 요구사항에 의해 간접적으로 영향을 받아 반드시 수정해야 정상적으로 작동하는 사항은 사용자에게 확인한 후, 해당 요구사항과 함께 작동하도록 변경 또는 추가한다.
- README.md는 프로젝트 전체 요구사항의 기준으로 사용한다.
- 각 웹페이지 구성 파일은 대응하는 `README_[file_name]` 문서를 1:1로 가진다.
- 파일을 생성, 수정 또는 삭제하기 전에 해당 파일과 대응하는 `README_[file_name]` 문서를 확인한다.
- 새로운 웹페이지 구성 파일을 생성할 경우 대응하는 `README_[file_name]` 문서도 함께 생성한다.
- 기존 기능을 수정할 때 관련 기능에 미치는 영향을 확인한다.
- 계산 결과의 정확성을 중요하게 취급한다.
- JSON 데이터 구조는 향후 항목이 추가될 수 있도록 확장 가능하게 설계한다.
- HTML, CSS, JavaScript의 역할을 가능한 한 명확하게 분리한다.
- 반복적으로 사용되는 계산 로직은 적절한 JavaScript 함수로 분리한다.
- 사용자에게 표시되는 UI와 명칭은 가능한 한 한국어를 우선한다.
- 프로젝트 구조나 데이터 형식이 변경되면 README.md 및 관련 `README_[file_name]` 문서도 함께 갱신한다.
- 기능을 추가하기 전에 기존 소스코드와 관련 요구사항 문서의 현재 상태를 확인한다.
- 코드 수정 시 기존에 구현되어 있는 기능을 불필요하게 제거하거나 변경하지 않는다.
- 요구사항이 모호하거나 계산 기준을 확인할 수 없는 경우 임의로 추측하지 않고 확인한다.

## 13. ChatGPT를 이용한 개발

이 Repository는 ChatGPT가 프로젝트의 현재 소스코드와 요구사항 문서를 확인하면서 개발을 이어갈 수 있도록 구성한다.

ChatGPT가 작업할 때는 다음을 원칙으로 한다.

1. 현재 Repository의 실제 파일과 README.md를 우선 확인한다.
2. 수정하거나 생성하려는 파일에 대응하는 `README_[file_name]` 문서가 있는지 확인한다.
3. 해당 `README_[file_name]` 문서의 요구사항과 기존 구현을 파악한 후 수정 범위를 결정한다.
4. 요구사항과 기존 구현이 충돌하는 경우 변경 전에 확인한다.
5. 명시하지 않은 사항은 임의로 해석하거나 결정하지 않는다. 요구사항의 간접적인 영향으로 반드시 필요한 변경이 있는 경우 사용자에게 확인한 후 함께 반영한다.
6. 필요한 파일만 수정한다.
7. 기능 변경 후 관련 코드와 요구사항 문서의 일관성을 확인한다.
8. 데이터 구조를 변경하는 경우 기존 JSON 데이터와의 호환성도 고려한다.
9. 구현되지 않은 기능을 이미 구현된 것처럼 기록하지 않는다.
10. 프로젝트의 현재 상태와 변경된 요구사항을 README.md 및 관련 `README_[file_name]` 문서에 반영한다.

## 11. 요구사항 문서 관리

README.md에는 프로젝트 전체에 적용되는 공통 요구사항과 개발 원칙을 기록한다.

구체적인 기능, 입력 항목, 계산 공식, 결과 표시 방식, UI/UX, JSON 상세 스키마 등 파일별 또는 기능별 세부 요구사항은 해당 기능을 구현하는 파일과 1:1로 대응하는 `README_[file_name]` 문서에서 관리한다.

따라서 세부 요구사항이 아직 정의되지 않았다는 이유로 README.md에 확정하지 않은 사항을 목록으로 나열하지 않는다.

새로운 요구사항이 확정되면 적절한 `README_[file_name]` 문서를 생성하거나 기존 문서를 갱신하고, 실제 소스코드와 해당 문서가 일치하는지 확인한다.
